## 1. 产品需求文档（PRD）

### 1.1 Purpose

定义 Manufacturing WMS Platform 的产品愿景、定位、目标与价值主张，为所有后续需求规格提供顶层指导。

### 1.2 Scope

平台级产品定义，涵盖目标市场、核心能力边界、商业目标，不涉及具体技术实现。

### 1.3 产品愿景

> **一句话愿景**：成为中大型制造企业从 ERP 库存管理迈向精细化仓储管控的**首选平台**，以"实时精准库存 + 智能任务调度 + 开箱即用的行业配置"为核心差异化能力。

### 1.4 产品定位

| 定位维度 | 定义 |
|----------|------|
| **市场定位** | 中大型制造企业仓储数字化平台（非 SaaS，非单客户定制） |
| **客户阶段** | 从 2.0（ERP 库存模块）向 3.0（专业 WMS）过渡的企业，部分触达 3.0→4.0 升级 |
| **差异化定位** | 制造业专属 WMS（不是通用物流 WMS）；线边仓深度管理；任务中心统一调度；行业配置包开箱即用 |
| **技术定位** | DDD + Modular Monolith，支持 5 年内逐步拆分为微服务 |
| **生态定位** | ERP 集成中枢（SAP/Oracle/金蝶/用友），向上承接 MES/QMS/TMS 等扩展 |

### 1.5 目标客户画像

| 客户属性 | 具体描述 |
|----------|----------|
| **企业规模** | 年营收 1~50 亿人民币的中大型制造企业 |
| **行业分布** | 汽车零部件、电子制造、机械装备为主；食品饮料、医药、化工为拓展方向 |
| **数字化现状** | 已部署 ERP（SAP/Oracle/金蝶/用友），库存管理停留在 ERP 模块；部分有 PDA 但未系统化 |
| **核心痛点** | 账物不符、缺料频发、线边仓失控、多仓割裂、批次追溯困难 |
| **采购动机** | 生产缺料导致停线成本 > WMS 投入成本；客户要求追溯能力；集团要求多仓统一管控 |
| **决策人** | 供应链总监 / 仓储经理 / IT 总监 |
| **部署偏好** | 私有化部署为主（数据安全顾虑）；部分接受混合云 |

### 1.6 产品目标（可量化）

| 目标ID | 目标描述 | 量化指标 | 时间线 |
|--------|----------|----------|--------|
| **GOAL-01** | 消除库存不透明，实现账实同步 | 库存账物相符率 ≥ 98%（上线 6 个月内） | v1.0 |
| **GOAL-02** | 消除生产缺料，保障准时供料 | 产线缺料停工次数降低 ≥ 50%（上线 6 个月内） | v1.0 |
| **GOAL-03** | 提升仓储作业效率 | 拣货效率提升 ≥ 30%（单/小时）；入库上架时效 ≤ 30 分钟 | v1.0 |
| **GOAL-04** | 建立平台可复用性 | 标准行业配置包覆盖 3+ 行业；单个客户配置上线周期 ≤ 4 周 | v1.0 |
| **GOAL-05** | 线边仓精细管控 | 线边仓缺料次数降低 ≥ 60%；线边库存周转天数缩短 ≥ 20% | v1.0 |
| **GOAL-06** | 集成零断点 | ERP 集成数据不一致率 ≤ 1%；集成部署周期 ≤ 2 周 | v1.0 |

├─────────────────────────────────────────────────────────┤

│  ┌──────────┐  ┌──────────┐  ┌──────────┐              │
│  │ 实时精准 │  │ 智能任务 │  │ 行业开箱 │              │

**四大价值主张详解：**

| 价值主张 | 目标客户痛点 | 平台能力 | 量化收益 |
|----------|------------|----------|----------|
| **实时精准库存** | P01 库存不透明、P06 多仓割裂、P11 FIFO 难执行 | 库位级实时库存 + 多维查询 + 批次追踪 + FIFO/FEFO 策略 | 账物相符率 ≥ 98% |
| **智能任务调度** | P04 配送混乱、P07 盘点低效 | 任务中心统一调度 + 优先级 + 异常挂起 + 负载均衡 | 拣货效率 +30% |
| **行业开箱即用** | 行业差异导致定制成本高 | 行业配置包 + 规则引擎 + 工作流引擎 | 配置上线 ≤ 4 周 |
| **ERP 集成零断点** | P12 集成断点 | 标准接口 + 数据一致性校验 + 事件驱动同步 | 数据不一致率 ≤ 1% |

### 1.8 Design Principles

1. **库存优先**：所有功能围绕"实时精准库存"展开，库存是平台的核心竞争力
2. **配置优于定制**：行业差异通过配置包解决，不通过代码分支
3. **任务驱动**：仓库作业统一建模为任务，通过任务中心管理生命周期
4. **集成友好**：与外部系统（ERP/MES）的集成是第一优先级，不是可选功能
5. **移动优先**：PDA 端是操作员的主要交互界面，Web 端是管理者的主要交互界面

### 1.9 Assumptions

| 假设ID | 假设内容 | 影响范围 | 验证方式 |
|--------|----------|----------|----------|
| ASM-01 | 目标客户已部署 ERP 且愿意集成 | 集成模块 | 客户访谈 |
| ASM-02 | v1.0 不覆盖保税仓/海关合规 | Warehouse 模块 | Phase 1 遗留问题确认 |
| ASM-03 | v1.0 不实现多语言/多货币 | 全平台 | 客户需求确认 |
| ASM-04 | 危化品法规 v1.0 仅基础覆盖 | Material/Warehouse | 行业配置包定义 |
| ASM-05 | 客户有 PDA 硬件或愿意采购 | PDA 端 | 客户访谈 |
| ASM-06 | 目标客户仓库层级为 3 级（仓→区→位） | Warehouse 模块 | Phase 1 调研验证 |

### 1.10 Risks

| 风险ID | 风险描述 | 影响 | 概率 | 应对策略 |
|--------|----------|------|------|----------|
| RSK-01 | 需求范围蔓延导致核心模块交付延期 | 高 | 中 | 严格 P0/P1/P2 优先级管理，P0 MVP 先行 |
| RSK-02 | 行业配置化边界不清晰导致过度设计 | 中 | 中 | 行业配置包分批交付，汽车/电子先行 |
| RSK-03 | ERP 集成复杂度超出预期 | 高 | 高 | 提前与主流 ERP 建立集成适配层；预留集成调试期 |
| RSK-04 | 目标客户数字化基础不足（无 ERP） | 中 | 低 | 提供"轻量 ERP"集成模式或独立运行模式 |
| RSK-05 | 验收标准量化指标难以精确测量 | 低 | 中 | 定义测量基线与测量方法，允许合理偏差 |

### 1.11 Alternatives

| 替代方案 | 描述 | 优劣 |
|----------|------|------|
| **方案 A** | 先聚焦汽车/电子行业深度落地，再横向扩展 | ✅ 降低 v1.0 范围风险；❌ 丧失平台化通用性 |
| **方案 B** | 将 P1 模块（Transfer/CycleCount）提前纳入 P0 | ✅ 提升平台完整性；❌ 延长 MVP 交付周期 |
| **方案 C** | SaaS 标准化版本，配置能力受限 | ✅ 降低部署复杂度；❌ 丧失制造业深度定制能力 |
| **选定方案** | P0 核心 MVP + 行业配置包 + P1/P2 分批交付 | 平衡完整性与交付速度 |

### 1.12 Review Items

| 评审项 | 评审标准 |
|--------|----------|

## 2. 业务需求规格（BRS）

### 2.1 Purpose

系统性定义各业务模块的功能需求，建立需求 ID 与优先级体系，为用户故事、业务规则和追踪矩阵提供结构化基础。

### 2.2 Scope

覆盖 P0 核心模块全部需求、P1 重要模块关键需求、P2 支撑模块关键需求、v2.0+ 未来模块需求预留。

### 2.3 Design Principles

1. **模块化组织**：需求按业务模块归类，与 Phase 1 模块体系对应
2. **优先级明确**：每条需求标注 P0/P1/P2，与 Phase 1 痛点关联
3. **可验证**：每条需求有明确的验收标准
4. **配置化标注**：标注需求的配置化程度（固定/可配置/可扩展）

### 2.4 模块优先级体系

| 优先级 | 模块 | 说明 |
|--------|------|------|
| **P0 核心** | Warehouse, Material, Inventory, Inbound, Outbound, TaskCenter | v1.0 MVP 必须交付 |
| **P1 重要** | Transfer, CycleCount, LineSideWarehouse, Production, Barcode/Label/Print | v1.0 交付但允许功能精简 |
| **P2 支撑** | Workflow, RuleEngine, Notification | v1.0 基础版本，后续迭代完善 |
| **v2.0+** | MES, QMS, TMS, OMS, Equipment, DigitalTwin, AI | 架构预留，需求仅定义接口与事件 |

## 3. 用户故事（User Stories）

### 3.1 Purpose

从用户视角描述功能需求，确保每条需求以用户价值为导向，而非功能清单导向。

### 3.2 Scope

P0 核心模块完整用户故事集（≥ 20 个）；P1/P2 模块关键用户故事（每模块 3~5 个）。

### 3.3 Design Principles

1. **角色覆盖**：涵盖仓库管理员、仓库主管、采购员、生产计划员、产线操作员、系统管理员、PDA 操作员 7 类角色
2. **价值导向**：每个用户故事必须说明价值（so that...）
3. **验收标准明确**：每个用户故事有 ≥ 2 个验收标准
4. **ID 可追踪**：用户故事 ID 与需求 ID（REQ）对应

### 3.4 角色定义

| 角色代码 | 角色名称 | 主要职责 | 主要交互终端 |
|----------|----------|----------|------------|
| WM | 仓库管理员 | 入出库操作、上架/拣货、盘点执行 | PDA + Web |
| WS | 仓库主管 | 库存监控、任务调度、审批、报表 | Web |
| PU | 采购员 | 采购订单管理、供应商协调 | Web |
| PP | 生产计划员 | 生产工单管理、领料计划、补料触发 | Web |
| LO | 产线操作员 | 线边领料、消耗确认、退料 | PDA |
| SA | 系统管理员 | 系统配置、主数据管理、权限管理 | Web |
| PO | PDA 操作员 | PDA 扫码执行仓库作业 | PDA |

| US-NT-002 | 作为 SA，我想要配置通知模板和通知规则，以便不同场景的通知内容专业且有针对性 | P2 | ①通知内容模板可编辑 ②通知规则按事件类型/角色/优先级配置 |
| US-NT-003 | 作为 WS，我想要查看通知历史记录，以便回顾重要通知处理情况 | P2 | ①所有通知留有发送记录 ②可按时间/类型/角色查询 |

### 3.8 Assumptions

| 假设 | 说明 |
|------|------|
| 用户故事覆盖 P0 所有核心场景 | 无重大场景遗漏 |
| P1/P2 用户故事为关键场景 | 次要场景在后续迭代补充 |
| 角色定义覆盖主要用户群体 | 未来可能新增质检员、物流员等角色 |

### 3.9 Risks

| 风险 | 应对 |
|------|------|
| 用户故事粒度过细导致数量过多 | P0 仅覆盖核心场景，次要场景以需求规格覆盖 |
| 角色定义不完整导致遗漏 | Phase 3 DDD 时补充角色与权限设计 |

### 3.10 Alternatives

| 替代方案 | 优劣 |
|----------|------|
| 用功能清单替代用户故事 | ❌ 丧失用户视角与价值导向 |
| 仅写 P0 用户故事 | ✅ 聚焦核心；❌ P1/P2 场景缺乏用户视角 |

### 3.11 Review Items

| 评审项 | 标准 |
|--------|------|
| P0 用户故事数量 ≥ 20 | ✅（24 个） |
| 每个用户故事有 ≥ 2 个验收标准 | 逐条检查 |
| 角色覆盖 7 类 | ✅ |
| 用户故事 ID 与需求 ID 可对应 | 逐条验证 |

### 3.12 Future Evolution

- Phase 3 DDD 时将用户故事映射为用例与领域事件
- 客户确认后可能补充行业专属用户故事
- v1.1+ 补充 P1/P2 完整用户故事集

## 4. 用例（Use Cases）

### 4.1 Purpose

描述核心业务场景的完整操作流程（含异常流程），为系统交互设计和领域事件识别提供输入。

### 4.2 Scope

5 个核心业务场景：入库、出库、调拨、盘点、线边仓配送。

### 4.3 Design Principles

1. **端到端**：每个用例覆盖从触发到完成的完整流程
2. **异常覆盖**：每个用例包含 ≥ 2 个异常流程
3. **角色明确**：每个步骤标注执行角色
4. **与 Phase 1 对应**：用例流程与 Phase 1 业务流程描述一致

## 5. 业务规则（Business Rules）

### 5.1 Purpose

定义平台必须遵守的核心业务规则，确保系统行为符合制造业仓储管理的业务逻辑与合规要求。

### 5.2 Scope

覆盖库存规则、入库规则、出库规则、分配规则、状态规则、审批规则 6 大类，≥ 30 条规则。

### 5.3 Design Principles

1. **可追溯**：每条规则标注适用场景与来源
2. **配置化标注**：标注规则的配置化程度（固定/可配置/可扩展）
3. **与 Phase 1 对应**：规则来源标注 Phase 1 痛点编号

### 5.4 库存规则

| 规则ID | 规则名称 | 规则描述 | 适用场景 | 配置化程度 |
|--------|----------|----------|----------|------------|
| BR-001 | **负库存禁止规则** | 出库数量不得超过可用库存数量（启用负库存开关时可配置允许负库存） | 所有出库操作 | 可配置 |
| BR-002 | **库存状态隔离规则** | 不同状态的库存（可用/冻结/待检/隔离）不可混合计算可用量 | 库存分配与查询 | 固定 |
| BR-003 | **在途库存不参与分配规则** | 调拨在途库存不计入源仓和目标仓的可用库存 | 跨仓调拨 | 固定 |
| BR-004 | **安全库存预警规则** | 当前可用库存 ≤ 安全库存值时自动触发预警通知 | 库存监控 | 可配置（阈值、通知渠道） |
| BR-005 | **临期预警规则** | 有效期距今 ≤ 预警天数时自动触发预警；预警天数可按物料配置 | 有效期管理物料 | 可配置 |
| BR-006 | **库龄预警规则** | 物料入库超过 N 天未消耗时触发预警；N 可配置 | 呆滞物料管理 | 可配置 |
| BR-007 | **零库存预警规则** | 库存为 0 且有待处理需求（领料单/销售订单）时触发预警 | 缺料场景 | 可配置 |
| BR-008 | **库存调整审批规则** | 盘盈/盘亏/报废/入库更正等调整操作必须经审批流审批 | 库存调整 | 可配置（审批流） |
| BR-009 | **库存冻结规则** | 冻结的库存（按批次/物料/库位）不可被分配算法选中出库 | 质量问题调查 | 可配置（冻结范围） |
| BR-010 | **库存流水不可删除规则** | 所有库存变动记录（流水账）不可修改、不可删除 | 审计合规 | 固定 |

### 5.5 入库规则

| 规则ID | 规则名称 | 规则描述 | 适用场景 | 配置化程度 |
|--------|----------|----------|----------|------------|
| BR-011 | **入库数量校验规则** | 入库数量不超过采购订单未入库余量 ×（1 + 超收比例）；超收比例可配置 | 采购入库 | 可配置 |
| BR-012 | **分批到货规则** | 一个采购订单允许多次入库（分批到货），累计入库数量不超过订单总量 ×（1 + 超收比例） | 采购入库 | 固定 |
| BR-013 | **批次号强制录入规则** | 启用批次管理的物料，入库时必须录入批次号；未启用批次管理的物料，批次号可选 | 入库操作 | 可配置（按物料） |

| BR-015 | **质检规则** | 入库时按质检策略（全检/抽检/免检）决定是否触发质检流程；质检策略按物料+供应商配置 | 入库质检 | 可配置 |
| BR-016 | **免检物料直接上架规则** | 免检物料（按供应商评级或物料类型配置）跳过质检步骤直接上架 | 免检入库 | 可配置 |

| BR-020 | **入库回传 ERP 规则** | 入库完成后自动回传 ERP 收货信息；回传失败时重试并通知 | ERP 集成 | 固定 |

## 6. 异常规则（Exception Rules）

### 6.1 Purpose

定义异常场景的触发条件、处理策略、通知机制与恢复流程，确保系统在异常情况下有明确的处理路径，不阻塞业务也不造成数据错误。

### 6.2 Scope

覆盖缺料、超收、短收、质检不合格、库存冻结、任务异常、系统故障等 ≥ 15 个异常场景。

### 6.3 Design Principles

1. **异常有路径**：每个异常场景有明确的处理策略和恢复流程
2. **通知到位**：异常触发时通知到相关角色
3. **不阻塞正常业务**：异常处理不影响其他正常流程
4. **数据一致性**：异常处理后数据状态一致

### 6.4 异常规则清单

| 规则ID | 异常场景 | 触发条件 | 处理策略 | 通知机制 | 恢复流程 |
|--------|----------|----------|----------|----------|----------|
| ER-001 | **缺料** | 可用库存 < 领料单需求量 | 系统拦截出库；生成缺料预警；推荐替代料（如有） | 站内消息+邮件通知 PP、PU、WS | 采购补货到货后重新执行领料；或使用替代料 |
| ER-002 | **超收** | 到货数量 > 采购订单余量 ×（1 + 超收比例） | 系统拦截入库；需 WS 审批 | 站内消息通知 WS、PU | WS 审批通过后放行；或拒收多余部分 |
| ER-003 | **短收** | 到货数量 < 采购订单数量（且低于容忍比例） | 系统记录差异；生成短收报告 | 站内消息通知 PU | PU 与供应商协商补货或接受短收 |
| ER-004 | **质检不合格** | 质检结果为"不合格" | 物料自动进入隔离区；状态标记"不合格" | 站内消息+邮件通知 PU、WS | 退货给供应商/返工/报废处理 |
| ER-005 | **库存冻结** | 因质量/合规原因冻结特定批次 | 冻结库存不可分配/出库；冻结原因必填 | 站内消息通知 WS、相关操作员 | 问题解决后审批解冻；或确认后报废 |
| ER-006 | **上架库位已满** | 推荐库位容量不足 | 系统重新推荐次优库位；若无可用库位则任务挂起 | 站内消息通知 WS | WS 手动指定库位或整理库位后恢复 |
| ER-007 | **拣货库位库存冻结** | 推荐拣货库位库存被冻结 | 系统自动跳过冻结库位，推荐次优可用库位 | 系统自动处理 | 无需人工干预 |
| ER-008 | **任务异常挂起** | 作业过程中发现异常（物料损坏/找不到/数量不符） | 操作员挂起任务；记录异常原因 | 站内消息通知 WS | WS 评估后恢复任务/关闭任务/创建新任务 |
| ER-009 | **任务超时** | 任务执行时间超过预期完成时间 | 系统标记超时；通知主管 | 站内消息+邮件通知 WS、PO | WS 跟进督促；或重新分配执行人 |
| ER-010 | **盘点差异超阈值** | 盘点差异金额超过配置阈值 | 自动触发复盘；需 WS + 财务双重审批 | 站内消息+邮件通知 WS、财务 | 复盘确认后审批调整 |
| ER-011 | **调拨在途超时** | 调拨出库后目标仓超过预期时间未入库确认 | 系统标记在途超时；通知主管 | 站内消息通知 WS | WS 跟进物流；确认到货后入库 |
| ER-012 | **线边仓缺料** | 线边仓库存低于最小值且主仓库存不足以补料 | 系统预警缺料；通知生产计划 | 站内消息+邮件通知 PP、PU | 紧急采购或从其他仓库调配 |
| ER-013 | **线边仓积压** | 线边仓库存超过最大值 | 系统预警积压；建议停止补料 | 站内消息通知 WS、PP | PP 调整生产计划消耗积压；或退料回主仓 |
| ER-014 | **ERP 集成失败** | ERP 接口回传失败（网络/数据/权限问题） | 系统记录失败；重试 3 次；重试失败后通知 | 站内消息+邮件通知 SA | SA 排查接口问题；手动触发重传 |
| ER-015 | **入库物料与采购单不符** | 到货物料编码/供应商与采购订单不匹配 | 系统拦截入库；生成差异报告 | 站内消息通知 PU、WS | PU 确认是否为合理差异（换料/供应商变更） |
| ER-016 | **标签打印失败** | 打印服务异常或打印机故障 | 系统记录打印失败任务；可手动重试 | 站内消息通知 PO、WS | 排查打印机问题后手动重试打印 |
| ER-017 | **批次号重复** | 入库时录入的批次号与已有批次号冲突 | 系统拦截；提示批次号已存在 | PDA 实时提示 | 操作员修正批次号或确认是否为同批次补货 |

### 6.5 Assumptions

| 假设 | 说明 |
|------|------|
| 异常规则覆盖主要异常场景 | 次要异常在实际运营中积累后补充 |
| 所有异常有通知机制 | 无"静默异常" |
| 异常处理不阻塞其他正常流程 | 异常任务独立处理 |

### 6.6 Risks

| 风险 | 应对 |
|------|------|
| 异常场景遗漏导致系统无处理路径 | 运营积累后持续补充 |
| 异常处理流程过于复杂导致操作员困惑 | 提供操作指引与异常处理 SOP |

### 6.7 Alternatives

| 替代方案 | 优劣 |
|----------|------|
| 所有异常统一挂起等人工处理 | ❌ 效率低；✅ 安全 |
| 部分异常自动处理（如库位冻结自动跳过） | ✅ 效率高；需确保自动处理逻辑正确 |

### 6.8 Review Items

| 评审项 | 标准 |
|--------|------|
| 异常规则数量 ≥ 15 | ✅（17 条） |
| 每条异常有处理策略与恢复流程 | ✅ |
| 每条异常有通知机制 | ✅ |
| 异常与 Phase 1 痛点可追溯 | 逐条验证 |

### 6.9 Future Evolution

- 运营积累后持续补充异常场景
- AI 辅助异常诊断与处理建议
- 异常统计分析报表
